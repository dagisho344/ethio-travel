# Phase 17A-2A/2B — granular user restriction foundation

## State and scope

`SUSPENDED` blocks an account; `DEACTIVATED` disables it without deleting history. A granular restriction leaves `User.status=ACTIVE` and the existing login/session valid. This checkpoint adds state, Admin-only API, and a reusable authorization policy. **No booking, review, messaging, or business mutation uses that policy yet.** Do not present these capabilities as enforced until 17A-2C. `PAYMENT_PROOF_SUBMISSION` is defined but has no current workflow; enforcement is deferred until that feature exists.

## Data model and migration review

`UserRestrictionCapability` has exactly `BOOKING`, `REVIEW`, `MESSAGING`, `BUSINESS_MANAGEMENT`, and `PAYMENT_PROOF_SUBMISSION`. `UserRestriction` stores one current row per `(userId, capability)` with reason, restricting Admin, restriction time, optional expiry, optional lift time/Admin/reason, and normal timestamps. Three named User relations use `ON DELETE RESTRICT`; no user rows, status values, existing tables, or credentials are changed. The unique constraint serves both the hot capability check and per-user Admin listing; no speculative secondary index is added. AuditLog records each episode, including re-restriction of the same state row.

Migration `20261003000001_user_restrictions` was reviewed and applied in 17A-2B with `prisma migrate deploy`. The development database now has 24 applied migrations, including the table and enum. No migration 25 was created. The pre-existing AI/verification defaults drift was excluded from this migration and remains outside this phase; migrations 1–23 and the migration lock retain their pre-application SHA-256 hashes.

## Effective state and Admin policy

Active means `liftedAt IS NULL AND (expiresAt IS NULL OR expiresAt > now)`. `expiresAt == now` is inactive. A single server timestamp is captured per read/transaction; no expiration job or JWT claim is required. Re-restricting an expired or lifted capability reuses the row and clears lift fields, while a new audit entry preserves the episode. A duplicate active restrict, stale lift, or second lift returns `409 Conflict`. A target-user row lock serializes restrict/restrict and restrict/lift even before a restriction row exists; unique `(userId, capability)` is a second guard. Database races were verified in 17A-2B using independent connections and a parent-row-lock barrier for restrict/restrict, lift/lift, restrict/lift, and expired re-restriction. Only valid serialized outcomes occurred, with one current-state row and matching audit history.

Admin may list restrictions for any existing user. Restrict requires an `ACTIVE` target without a current `ADMIN` role; `SUSPENDED` and `DEACTIVATED` targets may be viewed but not newly restricted. Lift is allowed for existing active restrictions even if the target status changed, so an Admin can clear policy before reactivation. Existing non-expired restrictions survive suspension/deactivation and become effective again if the account returns to `ACTIVE`. Product capabilities do not control Admin lifecycle endpoints. Neither restrict nor lift revokes sessions; future action boundaries must query current database state instead of trusting JWT claims.

## API, validation, and errors

All routes are under existing `AdminController` protection (`JwtAuthGuard`, `RolesGuard`, `AdminOnly`) and the existing `/api/v1` prefix:

| Route                                                     | Behavior                                                                                                                           |
| --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `GET /admin/users/:userId/restrictions`                   | List safe Admin state with computed `active`; 404 for missing user.                                                                |
| `POST /admin/users/:userId/restrictions`                  | Restrict one capability; accepts only `capability`, trimmed `reason` (1–1000), optional future ISO timestamp with explicit offset. |
| `POST /admin/users/:userId/restrictions/:capability/lift` | Lift an active capability; accepts only trimmed `reason` (1–1000).                                                                 |

UUID and enum route parameters are validated. The global whitelist rejects unknown body fields; actor IDs, lift/restriction times, and publication state are server-controlled. Mutations and audit entries are one Prisma transaction. Audit metadata is restricted to target ID, capability, and optional expiry; Admin reasons are in the bounded audit reason field, never in normal-user denial responses. `assertAllowed` is an **unwired foundation method** returning HTTP 403 with the existing Nest error-envelope fields plus `code=USER_CAPABILITY_RESTRICTED` and capability, without moderation reason. Socket.IO has no message-send event today; its current `WsException` pattern would need an equivalent safe capability code only if a future send event is introduced.
