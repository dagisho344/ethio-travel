# Destination booking-request configuration

The committed Phase 17C-1 schema, API contract, security design, and database verification are documented in [DESTINATION_BOOKING_REQUEST_CONFIG_PHASE17C.md](./DESTINATION_BOOKING_REQUEST_CONFIG_PHASE17C.md).

## Phase 17C-2 Admin interface

The Admin Destination editor at `/admin/destinations/:destinationId` and its edit page now include a booking-request configuration and manual payment-account panel. It uses the existing six Admin-only API operations through these same-origin BFF routes:

| Browser route                                                                   | Backend route                                                | Operations |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------ | ---------- |
| `/api/admin/destinations/:destinationId/booking-config`                         | `/api/v1/admin/destinations/:destinationId/booking-config`   | GET, PUT   |
| `/api/admin/destinations/:destinationId/payment-accounts`                       | `/api/v1/admin/destinations/:destinationId/payment-accounts` | GET, POST  |
| `/api/admin/destinations/:destinationId/payment-accounts/:accountId`            | Matching Admin account route                                 | PATCH      |
| `/api/admin/destinations/:destinationId/payment-accounts/:accountId/deactivate` | Matching Admin deactivate route                              | POST       |

The BFF validates UUIDs, limits provider values to TELEBIRR/CBE, rejects unknown fields and JSON bodies over 8 KiB, checks strict decimal-string prices and bounds account inputs. Account PATCH permits the backend's explicit Boolean `isActive` field for reactivation; account creation does not accept it. Deactivation sends no browser request body, as required by the BFF, which forwards an empty JSON object to the existing backend action. Mutations use existing same-origin validation and HttpOnly-session forwarding; responses use `Cache-Control: no-store`. Backend Admin guards and provider-specific account validation remain authoritative. Full account identifiers appear only in the authorized Admin edit form; account summaries are masked. Identifiers are not placed in URLs, telemetry, audit UI metadata, or browser logs.

The panel shows the actual Destination publication and booking-enabled states, ETB request price, `PER_BOOKING` unit, fixed quantity 1, request description, instructions, update time, and configuration completeness. Account cards include provider, holder, masked identifier, active state, display order, and optional instructions. Admins may create, edit, confirm deactivation, and confirm reactivation; no physical deletion occurs. The UI refreshes server state after successful mutations and after 409 conflicts. Account status changes never optimistically activate booking.

**Activation policy gate:** the booking-enabled control is disabled. Config PUT from this interface always sends `bookingEnabled: false`, and the BFF rejects any true value. The authoritative `DestinationBookingConfigService.updateConfig` also rejects `bookingEnabled: true` with HTTP 403 and stable code `DESTINATION_BOOKING_ACTIVATION_PAUSED`, before any configuration write or audit entry. Direct Admin API calls and other callers of this service cannot activate booking during the temporary policy gate. An already-enabled configuration is shown truthfully with a policy warning; its fields cannot be edited through the gated form, but an Admin may explicitly disable it after confirmation. Disabling preserves the price, description, instructions, and payment accounts and refreshes authoritative state; it is never a silent side effect. Draft saves and TELEBIRR/CBE account create, edit, deactivate, and reactivate remain available. Fulfillment and cancellation policies remain unapproved; any existing enabled state requires separate review. Configuration completeness does not imply admission, capacity, reservation, successful payment, or permission to activate booking.

Fixed UI text is localized in English and Amharic. Destination editorial text, account holder names, identifiers, request descriptions, and Admin-entered instructions are not automatically translated. Forms use semantic labels and responsive cards; deactivation confirmation supports Escape and trigger-focus return. Success and error feedback retranslate when the Admin changes locale without reloading.

Focused Phase 17C-2 tests cover BFF paths/validation, the 8 KiB body bound (including streamed requests), the false-only activation gate, explicit disable of an already-enabled configuration, both account providers, double-submit prevention, network failure, localization key parity, the enabled-state warning, deactivation/reactivation actions through their actual BFF route contracts, authoritative status refresh, stale-conflict refresh, locale-sensitive feedback, and Escape-key focus restoration. Run `node --test tests/admin-destination-booking-config.phase17c2.test.mjs` from `apps/web`. The final API policy correction passed 3/3 focused unit tests, 3/3 Admin HTTP tests, and 6/6 opt-in disposable-PostgreSQL tests. The PostgreSQL suite verified direct Admin HTTP rejection, unchanged configuration and audit rows on denial, existing enabled-row behavior, transactional account protection, and disposable-schema cleanup with unchanged main-schema counts. Focused web tests passed 16/16; API and web typechecks/builds and changed-file API lint passed. The web build retained only the known non-fatal Next.js ESLint-plugin detection warning.

### Browser acceptance (20 October 2026)

An authenticated Chrome browser used a disposable PostgreSQL schema migrated through all 27 existing migrations. The desktop English flow exercised initial disabled state, exact `1250.00` ETB draft save and reload, TELEBIRR and CBE creation, account editing, confirmed deactivation/reactivation, a duplicate-account 409 with authoritative refresh, invalid-price feedback, and explicit disabling of an already-enabled fixture. Before the backend policy gate was added, that fixture was created through the direct Admin API to verify truthful display; it was not enabled by the UI. The BFF rejected `bookingEnabled: true` with 403. The browser showed masked account identifiers on summary cards, while the authorized edit form showed full values. English and Amharic locale switching retranslated fixed labels and feedback without translating persisted content.

The mobile checks covered responsive layout and interactions, not a separate repetition of every account mutation. A fresh browser load produced no console errors, hydration exceptions, or failed network responses after adding the disposable Destination's Amharic editorial translation fixture. A literal two-Admin-tab stale edit was not run; the exercised duplicate-account 409 demonstrated the same server-authoritative conflict refresh path. The disposable fixture and browser services were removed after acceptance.

No Prisma schema or migration changes were made in Phase 17C-2; the database remains at 27 applied migrations. Traveler Destination booking requests, payment proof, payment verification, refunds, and video support remain deferred. Phase 17D must not infer approval of fulfillment or cancellation policy from this Admin configuration UI.
