## Canonical source and model

Region remains authoritative for its UUID, slug, status, timestamps and City
relationships. Its existing English/source `name` and nullable `description`
are unchanged. `RegionTranslation` stores only optional `displayName` (160),
nullable TEXT `description` (DTO limit 5,000), the existing `EditorialLocale`,
publication state and timestamps. English translation rows are not created or
backfilled. Only `am` is managed through the translation API.

The additive migration creates the new table, UUID primary key, unique
`(region_id, locale)`, `(locale, is_published)` B-tree index and a RESTRICT FK
to `regions` (ON UPDATE CASCADE, as generated by Prisma). `is_published`
defaults false; `created_at` defaults CURRENT_TIMESTAMP. UUID generation and
`updated_at` follow Prisma's client-side `uuid()`/`@updatedAt` conventions;
there is no SQL UUID or updated-at default. The SQL reuses `EditorialLocale`
and does not alter canonical columns, rewrite records, backfill, enable an
extension, or modify previously applied migrations.

### Safe generation method

Installed Prisma is 6.19.3. `migrate dev --create-only` was not used: that
workflow can inspect drift or apply pending history. A temporary snapshot of
the committed schema was compared to the new schema with:

```text
pnpm exec prisma migrate diff --from-schema-datamodel prisma/.g1a-baseline.prisma --to-schema-datamodel prisma/schema.prisma --script
```

This schema-to-schema operation does not use a live/shadow database. Its SQL
was reviewed and saved in the new migration directory; the temporary snapshot
was removed. No migration deployment/development/database-execute command ran.

## Public resolution

Existing routes support optional validated `locale=en|am`:

- `GET /api/v1/regions`
- `GET /api/v1/regions/:regionSlug`

Omitted locale/`en` always returns the source and does not load translations.
Explicit invalid values, including empty strings and wrong case, return 400.
The API does not read locale cookies or negotiate Accept-Language.

For `am`, the shared Region resolver requires:

1. Locale `am` and `isPublished=true`;
2. A nonempty trimmed translated display name;
3. A nonempty translated description if source description is nonempty.

Missing/draft/unpublished/incomplete records return the whole canonical
representation. No translated name is mixed with a required English paragraph.
If source description is null/empty/whitespace, translated description is
optional; an approved nonempty translated description is shown if present,
otherwise resolved description is null. Name and prose are the only overlaid
fields. Identity/status/timestamps remain canonical.

Both public paths continue querying only ACTIVE Regions. List matching and
ordering remain canonical, with the existing validated skip/take pagination.
Public loading uses explicit scalar selects and at most one published Amharic
relation row per Region, in bounded relation loading rather than N+1 queries.
Translation IDs, relation collections, publication fields and translation
timestamps are removed before public serialization. Admin source reads remain
canonical.

## Admin lifecycle

JWT + the existing ADMIN role guard protect:

- `GET /api/v1/admin/regions/:id/translations/:locale`
- `PUT /api/v1/admin/regions/:id/translations/:locale`
- `POST /api/v1/admin/regions/:id/translations/:locale/publish`
- `POST /api/v1/admin/regions/:id/translations/:locale/unpublish`

UUIDs and route locales are validated; `en` management is rejected. PUT's
allowlist contains only displayName and description. Null is accepted;
whitespace-only becomes null. Unknown fields are rejected by strict validation.
Lifecycle commands accept no body fields. Limits use the repository's
class-validator/class-transformer conventions.
The scoped Region command body pipe also rejects arrays/non-object bodies;
global validation and unrelated endpoints are unchanged.

Admin responses select only locale, text, isPublished, publishedAt and updatedAt.
A missing parent/translation returns 404. Draft save upserts through the unique
Region/locale key and always resets `isPublished=false, publishedAt=null`.
Publish locks/loads source, validates the saved translation and sets publication
time. Unpublish preserves the text and clears publication; repeating it on an
existing record is state-idempotent. A missing record is 404, consistent with
Destination lifecycle behavior.

ACTIVE/DRAFT/INACTIVE Regions allow translation lifecycle operations; a
non-ACTIVE parent still has no public representation. ARCHIVED permits read
and unpublish, but rejects save/publish. Translations never alter parent status.

## Source-edit invalidation and transactions

The existing canonical Region update service compares supplied name/description
to values read inside the transaction. Actual changes unpublish every currently
published translation and clear publication time, retaining draft text.
Resubmitting identical values, or changing only status/slug, does not invalidate.
Existing canonical source-name/slug generation is preserved; translation
operations never call that editing behavior.

Source edits and save/publish/unpublish lock the same canonical Region row with
a narrow parameterized `SELECT id ... FOR UPDATE`. This serializes publication
against source edits so publication cannot approve an old source concurrently
with invalidation. SQL binds the UUID and returns only the parent identifier.
Mutation and audit writes use the same Prisma interactive transaction.

New audit actions cover save, publish, unpublish and source-change invalidation.
Audit metadata contains Region ID, locale and limited lifecycle/operation values;
invalidation uses `source_changed`. Display names and descriptions never enter
audit metadata. AuditService is required, not optional. This is not a retrofit
of unrelated historical Region CRUD auditing.

## Security and scope boundaries

No authentication, business membership, media access, Booking/Payment/Refund,
availability, reviews, private trips/Budgets or TripShare behavior changes.
Search qualification/ranking/count/pagination and Map bounds/marker semantics
are unchanged. No Region translation matching or nested Search/Map localization
is implemented. `/shared-trip#token` remains independent and unchanged.

There are no City/Attraction/category/media translation models, web routes,
BFFs, message catalog edits, locale-prefixed URLs, owner-content translation,
machine translation, indexes for search, or PostgreSQL extensions.

### G1B local database verification

Prisma `migrate deploy` applied only `20260929000001_region_translations`.
Normal Prisma Client generation (6.19.3), Prisma validation and migration
status all completed successfully; the earlier Windows query-engine DLL `EPERM`
did not recur. Database catalog inspection confirmed the UUID primary key,
existing `EditorialLocale`, nullable `display_name`/`description`, publication
defaults, unique Region/locale key, locale/publication index and RESTRICT Region
foreign key. The canonical Region count remained 14 and its full-row SHA-256
fingerprint stayed unchanged immediately after deployment; the new translation
table was empty.

The opt-in `test/region-translations.database.e2e-spec.ts` exercises real
PostgreSQL with rollback-backed Region, translation, user and audit fixtures. A
separate deterministic-cleanup fixture verifies genuine Prisma transaction
rollback when audit persistence fails. The test suite covers public and Admin
HTTP behavior, fallback/completeness, publication, ARCHIVED/non-ACTIVE rules,
invalidation and persisted audit metadata; database constraints verify
unique/FK/RESTRICT behavior. Run it with:

```powershell
$env:DISCOVERY_DATABASE_TESTS = '1'
pnpm --dir apps/api exec jest --config test/jest-e2e.json --runInBand test/region-translations.database.e2e-spec.ts
```

The initial G1B test run exposed test-fixture issues: a synthetic JWT actor did

resulting canonical slug while verifying that translation publication remains
unchanged. Translation mutations themselves never alter slugs.

Parent-row `FOR UPDATE` locking is covered by code/unit inspection, but the
two-order cross-connection publish/source-edit race is **not** claimed as a
deterministic runtime test. It remains a focused follow-up before claiming
concurrency behavior under load.
