# Phase 17C-1: Destination booking-request configuration

This checkpoint provides Admin configuration and destination-specific manual payment accounts only. It does **not** create a DestinationBooking, accept traveler requests, collect money, verify a transfer, or promise a reservation. A future Destination booking is a **request** for an experience or visit: it reserves no capacity or inventory and guarantees neither admission nor fulfillment. An operator must explicitly accept or decline it in a later phase. Booking and payment states remain separate; submitting proof will not establish verified receipt. Cancellation/refund policy must be approved before traveler cancellation or paid-state transitions are implemented.

## Schema and migrations

Migration `20261014000001_destination_booking_config_accounts` (26) created `DestinationBookingConfig`, `DestinationPaymentAccount`, the `PER_BOOKING` price-unit enum, and the `TELEBIRR`/`CBE` provider enum. It was already applied before reconciliation and has not been edited. Migration `20261015000001_destination_request_description` (27) adds only nullable `request_description VARCHAR(1000)` and a CHECK requiring at least ten trimmed characters when `booking_enabled=true`. Existing disabled rows remain valid; no backfill or data deletion occurs. Both migrations are applied locally, with 27 current and no failed migration.

One config belongs to one Destination via a unique UUID FK with `ON DELETE RESTRICT`. `bookingEnabled` defaults false. `priceAmount` is nullable `Decimal(12,2)` while unconfigured and must be positive when present. Currency is fixed to ETB, and price unit is `PER_BOOKING`: the flat quote for **one booking request**, not per person, admission, or a confirmed reservation. `requestDescription` is Admin-managed editorial text explaining the requested experience, not an entitlement. It is nullable while disabled, but enabling requires a trimmed description of at least ten characters, a positive price, and one active syntactically valid payment account. `bookingInstructions` is optional. Both text fields are bounded to 1,000 characters. No automatic translation is performed.

Accounts are destination-specific, not shared. Each has a provider, bounded holder and identifier, normalized identifier, optional instructions, active state, display order, and timestamps. The unique `(destinationId, provider, normalizedIdentifier)` key prevents duplicates; the `(destinationId, isActive, displayOrder, id)` index supports ordered Admin listing. The Destination FK is `ON DELETE RESTRICT`. Accounts are deactivated, never physically deleted by this API. Future requests must snapshot the selected account and quote; account edits must not rewrite financial history.

## Identifier validation

These are **syntax rules only**, not proof of ownership, provider enrollment, or account validity:

- TELEBIRR accepts a mobile number written as `09` plus eight digits or `+2519` plus eight digits, with spaces/hyphens permitted as separators. Both normalize to `+2519` plus eight digits. The local/international 9-prefix forms follow [Ethio telecom's published mobile-number format](https://www.ethiotelecom.et/international-services/); [telebirr registration](https://www.ethiotelecom.et/telebirr/telebirr-registration/) uses a mobile number. Other formats require a separately reviewed policy change.
- CBE accepts 5–40 ASCII letters/digits after removing spaces/hyphens and uppercasing. This conservative, bounded rule does **not** claim to verify a CBE account or prescribe every CBE format. Significant account digits are never parsed as a number or rounded.

Original trimmed identifiers are retained for Admin display. Normalized identifiers are used for duplicate prevention. Neither identifiers nor holder names appear in audit metadata, error messages, or public API responses.

## Admin API

All routes are under `/api/v1/admin/destinations/:destinationId` and require `JwtAuthGuard`, `RolesGuard`, and `AdminOnly`. UUID paths and strict DTO allowlists reject malformed IDs and unknown fields. Missing or cross-Destination account IDs return scoped 404. Archived Destinations are readable but not mutable.

| Method | Path                                      | Contract                                                                                                                                                                                                                                                                                                                            |
| ------ | ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/booking-config`                         | Stored config or a disabled virtual default; does not create a row.                                                                                                                                                                                                                                                                 |
| PUT    | `/booking-config`                         | Full replacement: `bookingEnabled`, `priceAmount`, `requestDescription`, and `bookingInstructions` are required keys; the latter three may be `null` while disabled. Optional `currency`/`priceUnit`, if supplied, must be `ETB`/`PER_BOOKING`. Money is an exact two-decimal JSON string such as `"1500.00"`, never a JSON number. |
| GET    | `/payment-accounts?page=1&limit=20`       | Paginated Admin-only active and inactive accounts in stable order.                                                                                                                                                                                                                                                                  |
| POST   | `/payment-accounts`                       | Creates an active account by default.                                                                                                                                                                                                                                                                                               |
| PATCH  | `/payment-accounts/:accountId`            | Updates allowlisted fields, including `isActive` for explicit reactivation.                                                                                                                                                                                                                                                         |
| POST   | `/payment-accounts/:accountId/deactivate` | Empty body; deactivates an active account, or returns 409 if already inactive.                                                                                                                                                                                                                                                      |

Account responses use `Cache-Control: no-store` because they contain full Admin-only identifiers. No public/traveler account-detail endpoint or booking-offer projection is included in 17C-1. A future public offer must first satisfy existing published Destination and ACTIVE City/Region eligibility and expose only a deliberately safe projection. `bookingEnabled=true` is configuration readiness, **not** an executable traveler booking endpoint or confirmation of admission/payment.

## Transactions, audit, and privacy

Config PUT and every account mutation acquire the same parent Destination `SELECT ... FOR UPDATE` lock before reading or changing invariant-relevant state. Enabling requires a valid config and active account. PATCH/deactivate rejects removal of the last active account while enabled with 409; it never silently disables booking. Competing enable/deactivate operations therefore serialize. Config and account writes share a transaction with audit insertion; an audit failure rolls back the mutation.

Config audit distinguishes created, updated, enabled, and disabled. Account audit records created, updated, and deactivated. Metadata contains only safe Destination/config/account UUIDs and the enabled Boolean. No identifier, holder name, instructions, description, token, or full request body is audited. Accounts and configuration are not payment confirmation, and no new JWT claims or session behavior are introduced.

HTTP tests cover Admin/anonymous/traveler guards and strict request validation.
